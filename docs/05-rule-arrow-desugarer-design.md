## 1. 文档目的

本文定义 PathGuard Rules TOML 中重定向箭头语法的完整脱糖方案：

```toml
redirect = [
    "Download/source" -> "Download/target",
]
```

规则编译器必须把它转换为仅供内部解析的严格 TOML：

```toml
redirect = [
    { from = "Download/source", to = "Download/target" },
]
```

设计目标是在保留 `->` 用户认知优势的同时，保证：

- 字符串和注释中的 `->` 永远不会被误判。
- 只转换局部语法上完整的数组元素 `string -> string`。
- TOML 表路径和最终字段作用域仍由标准 TOML AST 判断。
- 生成文本是 D0 锁定的严格 TOML parser 可以解析的标准 TOML。
- 所有诊断最终指向原始 `rules.toml`，不暴露内部文本位置。
- 用户侧只存在箭头一种普通 redirect 写法。
- 扫描与重写保持线性复杂度，不构建第二棵 TOML 语法树。

本文只设计 `->`。不借此增加 `=>`、通配符、表达式、条件、优先级或其他 DSL 运算符。

## 2. 决策摘要

采用以下方案：

1. 使用流式最小 TOML 词法扫描器，不使用正则表达式或朴素字符串替换。
2. 不保存完整 `TokenStream`；扫描时只维护有限状态、容器栈、最近显著 token 和待完成箭头候选。
3. 只把位于直接数组元素位置的单行 TOML 字符串对识别为箭头候选。
4. 脱糖器理解数组、内联表和表头的局部标点上下文，但不解析 TOML 表路径、字段名或 dotted key。
5. 局部箭头错误优先于标准 TOML parse；存在箭头错误时不生成部分转换结果。
6. 合法候选转换为 `{ from = ..., to = ... }`，操作数字符串按原始字节复制，不重新转义或解码。
7. RewriteMap 使用生成字节区间到原始字节区间的有序分段映射。
8. `GeneratedRedirect` 只保存语义诊断和 AST 绑定所需的最小来源信息，不承担通用位置映射。
9. 标准 TOML 解析后先验证所有 generated node 的 AST 作用域，再执行普通字段类型解码。
10. v1 拒绝用户手写 `{ from, to }`，避免两套等价配置语法。
11. Phase D0 已用同一 binder-neutral 语料完成 C++/toml++ 与 Rust/`toml_edit::Document` 比较；生产只保留 C++20 + toml++ v3.4.0。
12. Rust 候选曾覆盖从规则源字节到已验证 PolicyBlob 的完整纯编译链；因额外工具链、C ABI、体积和完整编译资源成本未被选择，原型已删除。
13. Formatter、PathGuard 自建无损 CST 和 token 重写属于独立后续能力，不进入首版脱糖器。

总体流程：

```text
SourceBuffer
    -> RulesFormatProbe
    -> StreamingArrowLexer
    -> LocalArrayElementValidator
    -> Rewrite[]
    -> Desugared TOML + RewriteMap + GeneratedRedirect[]
    -> locked strict TOML parser
    -> GeneratedNodeScopeValidator
    -> RulesDocumentDecoder
    -> Canonical Policy IR
```

这些名称表示职责，不要求每一项都实现成类。无状态步骤优先使用纯函数和小型值对象。

### 2.1 本文回答的问题边界

本文首先回答：

> 在保留 `->` 的前提下，能否把它实现成安全、确定、可诊断且不进入运行时热路径的有限语法扩展？

答案是：在本文约束和测试全部满足时，可以。

但这不自动回答另一个产品问题：

> `->` 带来的方向可读性，是否值得承担专用词法扫描、RewriteMap、generated node 绑定和长期测试维护成本？

“能够安全实现”和“值得实现”是两个独立结论。Phase D0 不只是依赖验证，也是箭头语法的最终投入产出决策点；在它通过之前，不应把本设计视为不可逆的既定实现。

箭头价值也不应简化为“少写几个字符”。它主要解决的是安全规则中的方向辨识：

```text
应用看到的路径 -> 实际 backing 路径
```

对于手机文本编辑器、Root 文件管理器和终端手工维护场景，`->` 比 `=` 更直接表达数据流向，能减少把 source/target 写反的风险。该用户价值必须与控制面实现成本一起评估。

### 2.2 严格 TOML 替代方案

Phase D0 必须同时保留以下替代方案作为基准，而不是只验证箭头实现是否可行：

| 方案 | 用户示例 | 优点 | 代价 |
|---|---|---|---|
| PathGuard 箭头 | `"A" -> "B"` | 方向最直观、一行一条 | 需要本文全部控制面基础设施 |
| 标准 inline table | `{ from = "A", to = "B" }` | 零自定义语法、标准诊断 | 更长，手机端手写和快速扫读较弱 |
| 标准映射子表 | `"A" = "B"` | 严格 TOML、一行一条 | `=` 更像赋值/相等；source 被编码为动态 key |

D0 已证明关键依赖可靠并确认箭头方向表达的手工编辑价值，结论为采用箭头并进入 D1。严格 TOML 方案不作为并存的第二输入语法；未来只有通过新格式版本和价值复审才能替换箭头。

### 2.3 Phase D0 Go/No-Go 条件

本节保留为已执行的决策门槛。2026-07-26 的结果是全部通过：toml++ 的 table/value source region 在共同 Unicode/CRLF/BOM golden 中稳定，不需要隐藏标记；固定输入生成 207-byte policy v5；Android arm64 和 Zygisk 隔离验证通过。完整数据见 D0 决议。

满足以下条件才允许进入 D1：

1. 至少一个完整候选对生成 inline table 或其两个 value 提供稳定且可自动测试的 generated byte span。
2. Unicode、CRLF、BOM、同行和跨行箭头的 generated position 都能无歧义映射回原始 byte span。
3. generated node 可以一一绑定，不需要在正常路径全面依赖隐藏标记。
4. 字符串边界扫描可以严格复用 TOML 1.0 词法规则，不需要解释 table key 或建立第二棵 CST。
5. Rust 候选能够锁定 TOML 1.0 语义、不可变 Document span 生命周期、Android arm64 构建和 C ABI 所有权；C++ 候选能够锁定 toml++ 无异常模式与 source-region 转换。
6. 选定原型在建议 CPU/内存/体积预算内，并证明 parser、Rust runtime（如采用）和诊断代码不会链接进入 Zygisk 数据面。
7. 选定完整编译器对固定输入生成当前 207-byte `policy.bin format v5` golden，并可被现有 C++ reader 独立验证。

出现以下任一情况必须暂停 D1，重新比较严格 TOML，而不是因为存在 fallback 就默认继续：

- 两个候选的 generated span 在实际支持的 Unicode/CRLF/BOM 组合下都不稳定。
- Rust 候选必须转换为会清除 span 的 `DocumentMut` 才能完成 scope/decode，或者 Cargo 依赖无法冻结 TOML 1.0 语义。
- 普通 generated node 绑定必须全面依赖随机隐藏字段。
- 精确诊断必须引入完整轻量 CST 或解析 TOML 表路径。
- 生成位置无法稳定恢复到原始规则和两个操作数。
- 唯一 C ABI 仍需暴露 AST、RewriteMap、RulesDocument、Canonical Policy 或跨语言长期借用。
- D0 原型复杂度已经明显超出本文冻结的最小职责边界。

隐藏标记仍可作为技术备选进行验证，但“需要启用隐藏标记”本身是一次架构复审触发器，不是自动通过条件。

### 2.4 后续价值复审

即使 D0 通过，箭头的长期价值仍取决于实际编辑方式。以下情况应在下一次用户规则格式升级前重新评估：

- Manager 成为绝大多数配置修改入口，用户很少直接编辑文本。
- 用户反馈更偏好严格 TOML 工具兼容性，而不是箭头方向表达。
- 脱糖器维护成本持续高于规则语义编译器本身。
- 锁定 parser 升级反复破坏 generated span、TOML 版本边界或位置映射。

复审不能通过同时开放两套语法来规避决策。若未来删除箭头，应通过新的规则格式版本和一次性迁移完成，不在同一 format 中长期双轨运行。

## 3. 设计目标与非目标

### 3.1 设计目标

1. 精确识别字符串、注释和普通语法之间的 `->`。
2. 支持单行基本字符串和单行字面量字符串作为操作数。
3. 允许箭头两侧跨物理行的 TOML 空白。
4. 允许数组元素前注释和元素后行尾注释。
5. 拒绝表达式内部注释、链式箭头、缺失操作数和缺失元素分隔符。
6. 不把普通键值、内联表字段或表头中的箭头转换为嵌套内联表。
7. 脱糖后的文本必须由配置锁定版本的严格 TOML parser 解析。
8. parser、scope、type 和 semantic 诊断使用同一套原始源码坐标。
9. 无箭头输入不分配 Rewrite/GeneratedRedirect，并保持字节不变。
10. 扫描、候选验证和文本生成总计为 O(N)。

### 3.2 非目标

- 不解析 `[apps."package"]`、dotted key 或 TOML 表继承关系。
- 不验证普通整数、布尔值、日期时间或数组元素类型。
- 不在扫描阶段判断当前字段是否名为 `redirect`。
- 不支持多行字符串作为 redirect 操作数。
- 不允许用户手写内部 `{ from, to }` 结构。
- 不为未来 formatter 保存完整 token/trivia 流。
- 不提供通用宏、运算符优先级或表达式系统。
- 不在脱糖器中规范化路径或检查 redirect 冲突。

## 4. 用户语法契约

### 4.1 基本语法

v1 箭头表达式定义为：

```text
redirect_element = single_line_toml_string,
                   toml_whitespace*,
                   "->",
                   toml_whitespace*,
                   single_line_toml_string;
```

这里的 `toml_whitespace` 只包括空格、tab、LF 和 CRLF，不包括注释。

合法示例：

```toml
redirect = [
    "A" -> "B",
    'C'->'D',
    "Long/source"
        -> "Long/target",
]
```

### 4.2 局部数组元素约束

箭头表达式必须是某个 TOML value array 的直接元素。除空白和允许位置的注释外：

- 左操作数之前必须是该数组的 `[` 或 `,`。
- 右操作数之后必须是该数组的 `,` 或配对 `]`。
- 文件在右操作数之后直接结束时，可以先完成候选转换，再由锁定 TOML parser 报告未关闭数组。

约束针对的是数组 frame，而不是单纯检查字符。表头的 `[`、内联表中的 `,` 或嵌套容器的结束符不能冒充 redirect 元素边界。

### 4.3 注释位置

允许：

```toml
redirect = [
    # element comment
    "A" -> "B", # trailing comment
]
```

v1 拒绝：

```toml
redirect = [
    "A" # comment inside expression
        -> "B",
]
```

```toml
redirect = [
    "A" -> # comment inside expression
        "B",
]
```

表达式内部注释会增加重写、格式化和注释归属的歧义，没有当前必要。

### 4.4 字符串内部箭头

以下规则的源路径包含字面 `->`：

```toml
redirect = [
    "Download/name -> old" -> "Download/target",
]
```

扫描器只把字符串外、`Normal` 状态中的第二个箭头识别为运算符。

### 4.5 唯一用户语法

v1 只接受：

```toml
"A" -> "B"
```

不接受：

```toml
{ from = "A", to = "B" }
```

如果未来 redirect 需要 `read_only`、`create_target` 等属性，应使用独立、版本化的高级字段，例如 `redirect_rules`，而不是让普通 `redirect` 数组同时维护两套等价写法。

### 4.6 复杂度上限

`redirect_rules` 等高级标准 TOML 字段不经过箭头脱糖器，也不增加新的 generated node 类型。脱糖器永久只认识一条表层规则：

```text
direct value-array element: single-line-string -> single-line-string
```

未来产品能力增长只能修改 RulesDocumentDecoder、语义校验器和 Canonical Policy 映射，不能把 `priority`、条件、通配符或动作属性塞进箭头表达式。该约束把脱糖器的长期变化限制为错误修复、TOML 边界兼容和诊断改进。

## 5. 职责边界

### 5.1 脱糖器负责

- TOML 字符串和注释边界的词法识别。
- value array、inline table、table header 的浅层容器识别。
- `string -> string` 的局部数组元素完整性检查。
- 箭头专用诊断。
- 生成严格 TOML 文本。
- 生成 RewriteMap 和 GeneratedRedirect 来源记录。

### 5.2 锁定的严格 TOML parser 负责

- 完整 TOML 语法。
- key、quoted key、dotted key 和 table path。
- 数字、布尔、日期时间和普通数组/内联表。
- 重复键、重复表和标准 TOML 结构错误。
- 构建标准 TOML AST。

### 5.3 Generated node scope validator 负责

- 找到脱糖生成的 inline table 节点。
- 验证节点最终 AST 路径是否为 `/apps/<package>/redirect/<index>`。
- 优先报告箭头 scope 错误并抑制同一节点的派生类型错误。
- 拒绝未由脱糖器生成的手写 inline table。

### 5.4 语义编译器负责

- 包名、users、processes 和 capability 字段解码。
- 路径规范化。
- deny/redirect 冲突。
- Policy Requirements 和 Canonical Policy 构建。

## 6. Format 引导扫描

脱糖器入口由 `format` 选择。引导扫描器只识别文件第一个非 BOM、非空白、非注释声明：

```toml
format = 1
```

v1 约束：

- 允许文件开头 UTF-8 BOM。
- `format` 必须使用 bare key。
- 值必须是十进制整数 `1`。
- 声明必须是第一个有效声明。
- 缺失、首声明类型错误和未知版本在主扫描前失败。
- 后续重复 `format` 不由引导扫描器搜索，交给标准 TOML parser/decoder 按重复键错误处理。

引导扫描器不解释其他键，也不根据未来字段猜测格式版本。每个格式版本拥有冻结的脱糖入口。

## 7. 流式词法扫描器

### 7.1 为什么不保存完整 TokenStream

箭头识别只依赖局部邻域：

```text
array delimiter -> source string -> arrow -> target string -> array delimiter
```

因此首版不需要 `vector<Token>` 保存文件中的所有 key、数字、标点和 trivia。扫描器只保存：

- 当前词法状态。
- 有界容器栈。
- 最近两个显著 token 的摘要。
- 一个待完成箭头候选。
- 已确认 Rewrite 和 GeneratedRedirect 列表。
- 有界诊断列表。

额外内存为 O(R + D)，其中 R 是箭头规则数，D 是容器嵌套深度，而不是 O(全部 token 数)。

### 7.2 词法状态

```cpp
enum class LexState : std::uint8_t {
    kNormal,
    kBasicString,
    kLiteralString,
    kMultilineBasicString,
    kMultilineLiteralString,
    kComment,
};
```

只有 `kNormal` 状态中的连续 ASCII 字节 `-`、`>` 才构成箭头。

### 7.3 字符串边界

扫描器不解码 TOML 字符串值，但必须严格遵循锁定 TOML 版本的字符串边界规则。

#### 单行基本字符串

- 由 `"` 开始和结束。
- `\"` 不结束字符串。
- 结束引号前连续反斜杠数量的奇偶性必须正确处理。
- 非法 escape 由锁定 TOML parser 报告，扫描器只保证边界不漂移。

必须正确区分：

```toml
"A\" -> still string" -> "B"
"A\\" -> "B"
"A\\\" -> still string" -> "B"
```

#### 单行字面量字符串

- 由 `'` 开始和结束。
- 不处理反斜杠转义。
- 字符串内 `->` 永远是普通字节。

#### 多行基本字符串

- 由 `"""` 开始。
- 按 TOML 1.0 连续引号规则识别结束 delimiter。
- 处理反斜杠对 delimiter 判断的影响。
- 内容中的 `#` 和 `->` 不产生 comment/arrow token。

#### 多行字面量字符串

- 由 `'''` 开始。
- 按 TOML 1.0 连续单引号规则识别结束 delimiter。
- 内容中的 `#` 和 `->` 不产生 comment/arrow token。

多行字符串可以出现在文件其他位置，但不能作为 redirect 操作数。

### 7.4 注释

在 `kNormal` 状态遇到 `#` 后进入 `kComment`，直到 LF、CRLF 或 EOF。

注释中的引号、括号和箭头全部忽略：

```toml
# [ { "A" -> "B" } ]
```

### 7.5 显著 token

扫描器不保存完整 token，只对局部判断保留以下摘要：

```cpp
enum class SignificantKind : std::uint8_t {
    kString,
    kMultilineString,
    kArrow,
    kOpenArray,
    kCloseArray,
    kOpenInlineTable,
    kCloseInlineTable,
    kComma,
    kEquals,
    kDot,
    kOther,
};

struct SignificantToken {
    SignificantKind kind;
    SourceSpan span;
    std::uint32_t frame_id;
};
```

空白不成为显著 token。注释通常也不成为显著 token，但扫描器必须记录它是否出现在 source/arrow/target 内部间隙。

### 7.6 容器栈

```cpp
enum class FrameKind : std::uint8_t {
    kValueArray,
    kInlineTable,
    kTableHeader,
    kArrayTableHeader,
    kUnknownBracket,
};
```

扫描器不解析表头内容，只区分方括号当前属于 value array 还是声明表头。

除容器栈外只需维护两个布尔上下文：

```text
at_statement_start
expecting_value
```

`expecting_value` 在当前语句的 `=`、value-array 的 `[`/`,`、inline-table 的 `=`/`,` 后为 true。容器栈为空时，换行结束当前 TOML key/value 语句并清除该状态；容器内部的换行只作为 trivia。只有容器栈为空、当前不等待 value 且位于新语句起点时，`[` 才按 table header 处理。非法的跨行 key/value 最终仍由锁定 TOML parser 诊断，扫描器不尝试修复。

最小判定规则：

- 语句起始、容器栈为空时出现 `[`：table header。
- 语句起始、容器栈为空时出现 `[[`：array-of-tables header。
- `=` 后出现 `[`：value array。
- value array 的 `[` 或 `,` 后出现 `[`：嵌套 value array。
- inline table 的 `=` 或 `,` 后出现 `[`：value array。
- 无法可靠分类的 `[` 标记为 `kUnknownBracket`，其中不允许箭头转换。

每个 frame 分配单次扫描内唯一的递增 `frame_id`。箭头元素的左右分隔符必须属于同一个 `kValueArray` frame。

容器栈只用于局部标点关系，不保存或解释 table key。

## 8. 流式候选状态机

### 8.1 最小状态

```cpp
struct PotentialLeftOperand {
    SourceSpan string_span;
    SignificantToken prefix;
    std::uint32_t array_frame_id;
    bool comment_after = false;
};

struct PendingArrow {
    SourceSpan source_span;
    SourceSpan arrow_span;
    std::uint32_t array_frame_id;
    bool comment_before_arrow = false;
    bool comment_after_arrow = false;
};

struct PendingCandidate {
    SourceSpan source_span;
    SourceSpan arrow_span;
    SourceSpan target_span;
    std::uint32_t array_frame_id;
};
```

实现不必同时持有三个对象；它们表达三个逻辑阶段：

```text
可能的左字符串
    -> 已见合法箭头，等待右字符串
    -> 已见右字符串，等待元素终止符
```

任一时刻最多存在一个未完成候选。

### 8.2 左操作数检查

遇到外部 `->` 时：

1. 前一个显著 token 必须是单行字符串。
2. 该字符串之前的显著 token 必须是同一 value array frame 的 `[` 或 `,`。
3. 字符串和箭头之间只能有空白，不能有注释。

失败分类：

- 没有左字符串：`PG-ARROW-OPERAND`。
- 左字符串不在直接数组元素开始位置：`PG-ARROW-CONTEXT`。
- 间隙存在注释：`PG-ARROW-COMMENT-INSIDE`。

### 8.3 右操作数检查

合法外部箭头之后：

1. 下一个显著 token 必须是单行字符串。
2. 箭头和字符串之间只能有空白，不能有注释。
3. multiline string、number、boolean、array 或 inline table 均不是合法操作数。

失败统一定位箭头和实际 token，并报告 `PG-ARROW-OPERAND`；注释使用更具体的 `PG-ARROW-COMMENT-INSIDE`。

### 8.4 元素结束检查

右字符串之后跳过空白和注释，下一显著 token 必须是：

- 同一 value array frame 的 `,`；或
- 关闭同一 frame 的 `]`。

如果下一个 token 是：

- `Arrow`：`PG-ARROW-CHAINED`。
- `String`：`PG-ARROW-MISSING-COMMA`。
- 其他 token：`PG-ARROW-CONTEXT`。

右字符串后的注释合法，因为它属于整个数组元素，而不是 source/arrow/target 内部。

### 8.5 EOF 处理

- EOF 出现在箭头之后、右字符串之前：`PG-ARROW-OPERAND`。
- EOF 出现在完整右字符串之后，但 value array 未关闭：候选可以转换，由锁定 TOML parser 报告缺失 `]`。
- EOF 出现在未终止字符串中：停止箭头处理并报告字符串边界诊断，不能猜测后续箭头。

### 8.6 链式箭头

```toml
redirect = [
    "A" -> "B" -> "C",
]
```

右字符串后遇到第二个 Arrow 时直接报告 `PG-ARROW-CHAINED`。不得先生成第一段 rewrite，也不得继续标准 TOML parse。

## 9. 局部上下文示例

### 9.1 普通键值

```toml
foo = "A" -> "B"
```

左字符串前是 `=`，不属于 value array 元素：

```text
PG-ARROW-CONTEXT
```

### 9.2 内联表字段

```toml
foo = { bar = "A" -> "B" }
```

左字符串前是 inline table 中的 `=`：

```text
PG-ARROW-CONTEXT
```

### 9.3 表头

```toml
["A" -> "B"]
```

方括号 frame 是 `kTableHeader`，不是 `kValueArray`：

```text
PG-ARROW-CONTEXT
```

### 9.4 非 redirect 数组

```toml
deny = [
    "A" -> "B",
]
```

局部数组元素语法合法，因此可以脱糖；AST scope validator 随后报告：

```text
PG-RULE-ARROW-SCOPE
```

### 9.5 嵌套数组

```toml
foo = [
    ["A" -> "B"],
]
```

箭头是内层 value array 的直接元素，局部语法合法；AST 路径不是直接的 `apps.*.redirect/<index>`，随后报告 scope 错误。

### 9.6 缺少逗号

```toml
redirect = [
    "A" -> "B"
    "C" -> "D",
]
```

第一条目标字符串后的显著 token 是另一个字符串：

```text
PG-ARROW-MISSING-COMMA
```

## 10. Rewrite 生成

### 10.1 不生成完整 token 流

扫描阶段每确认一条候选，只追加一个 Rewrite 描述：

```cpp
struct ArrowRewrite {
    RuleId id;
    SourceSpan rule_span;
    SourceSpan source_span;
    SourceSpan arrow_span;
    SourceSpan target_span;
};
```

这里的 `RuleId` 只要求在单次编译内稳定，可以是递增整数，不需要跨编辑哈希或持久化身份。

扫描结束且没有箭头错误后，按 `rule_span.begin` 排序并验证区间不重叠，再一次性生成输出文本。

### 10.2 标准 TOML 输出

每条规则输出：

```text
{ from = <raw-source-string>, to = <raw-target-string> }
```

关键约束：

- `<raw-source-string>` 和 `<raw-target-string>` 直接复制原始 TOML string token 字节。
- 不解码后重新编码，避免改变转义、引号风格或 Unicode 字节。
- source/arrow/target 之间的原始空白被合成语法替换。
- 生成 inline table 始终位于单个物理行，满足 TOML 1.0 inline table 要求。
- 原始数组逗号、右括号和元素后注释不属于 rewrite 区间，原样保留。

跨行输入：

```toml
"A"
    -> "B"
```

生成：

```toml
{ from = "A", to = "B" }
```

生成文本行数可以改变，位置恢复由 RewriteMap 负责。

### 10.3 单次输出

不得对 `std::string` 反复执行中间 `insert` 或 `replace`。实现应：

1. 计算合成语法的总增量。
2. `reserve(source_size + generated_overhead)`。
3. 按原始偏移依次复制未修改区间和生成区间。

复杂度为 O(N + R)，不会退化为 O(N²)。

### 10.4 无箭头快路径

如果没有 ArrowRewrite：

- 不分配生成文本副本，允许 parser 直接读取原始 SourceBuffer。
- RewriteMap 使用恒等映射或空映射约定。
- GeneratedRedirect 为空。

具体 API 可以用 `std::string_view` 指向原始内容，避免无意义复制。

## 11. RewriteMap

### 11.1 内部坐标

所有内部位置统一使用 UTF-8 字节半开区间：

```cpp
struct ByteSpan {
    std::uint32_t begin;
    std::uint32_t end;
};
```

源文件大小受 `RulesLimits` 限制，使用 32 位偏移足够且比 `size_t` 更稳定。所有加法在写入 32 位字段前执行溢出检查。

### 11.2 分段映射

```cpp
enum class RewriteSegmentKind : std::uint8_t {
    kCopied,
    kSyntheticRule,
    kSyntheticArrow,
};

struct RewriteSegment {
    ByteSpan generated;
    ByteSpan original;
    RewriteSegmentKind kind;
};
```

分段按 `generated.begin` 严格递增且不重叠。位置查询通过二分查找完成：

```text
generated offset
    -> upper_bound(segments)
    -> original offset/span
```

普通复制区间做线性偏移映射；合成区间映射到原始整条规则或箭头 span。

### 11.3 推荐映射

| 生成片段 | 原始映射 |
|---|---|
| `{ from = ` | 原始整条箭头规则 |
| source string | 原始 source string，一对一 |
| `, to = ` | 原始 arrow span |
| target string | 原始 target string，一对一 |
| ` }` | 原始整条箭头规则 |

parser 如果在合成字段附近报错，用户应看到整条规则或箭头，而不是无意义的内部 `from`/`to` 列位置。

### 11.4 LineIndex 与显示列

原始和生成文本各自维护一个 `LineIndex`。内部统一使用 byte offset；只有 parser 不直接返回 byte range 时，才需要把其 line/column 转为 generated byte offset。

内部和 JSON 诊断必须包含原始 byte offset。CLI 文本显示使用：

- 1-based 行号。
- 1-based Unicode code point 列号。

如果未来提供 LSP，适配层再转换为 UTF-16 code units；核心 SourceSpan 不存储 LSP 坐标。

Rust 候选的 `toml_edit::Document` 节点和 parse error 直接返回 generated `Range<usize>`；C++ 候选需要验证 toml++ source position 到 generated byte offset 的转换规则。两者都必须通过 Unicode、CRLF 和 BOM golden，不能因 API 已声明 byte span 就跳过端到端映射测试。

### 11.5 成功路径约束

RewriteMap 的 generated-to-original 二分查询只用于 parser/diagnostic 位置恢复，不参与正常 RulesDocument 构建、路径规范化、冲突检测或 Policy 编码。

成功路径中的 generated node 绑定直接使用 `GeneratedRedirect.generated_*` 精确索引或已冻结的 binder，不通过 RewriteMap 反复查询。性能测试应断言无诊断的成功编译不会调用通用 `MapGeneratedPosition()`；未来重构若把该查询移入成功热路径，需要单独说明理由和基准数据。

## 12. GeneratedRedirect 来源记录

RewriteMap 解决任意 parser 位置映射；GeneratedRedirect 解决 redirect 语义来源和 AST 绑定。两者职责不同，不能只保留其中一个。

最小结构：

```text
GeneratedRedirect {
    id: RuleId
    original_rule: ByteSpan
    original_source: ByteSpan
    original_arrow: ByteSpan
    original_target: ByteSpan
    generated_table: ByteSpan
    generated_source: ByteSpan
    generated_target: ByteSpan
}
```

这些 span 用于：

- AST inline table 与某条箭头规则绑定。
- 整体 table source region 不足时，通过两个 generated value span 组合绑定。
- `from`、`to` 路径语义错误分别指向原始操作数。
- 冲突诊断关联两条原始规则。
- 区分脱糖生成 inline table 与用户手写 inline table。

这不是完整 token 模型，也不保存普通 TOML 节点来源。

## 13. TOML parser 集成与 generated node 绑定

### 13.1 Phase D0 共同语料

在实现生产 adapter 前先冻结 binder-neutral golden。语料只断言外部行为：

- 每条 GeneratedRedirect 恰好绑定一个正确 AST node。
- 原始 source/target/rule span 恢复一致。
- 手写 inline table 不会被误绑定。
- Unicode、CRLF、BOM、同行/跨行箭头和多次 rewrite 后结果稳定。
- 标准 TOML parse error 经 RewriteMap 返回相同原始 byte span。
- 选定完整编译器生成当前 207-byte `policy.bin format v5` golden。

C++/toml++、Rust/`toml_edit` 和任何受控 fallback 原型都必须使用同一套语料与断言。不得在知道结果后为某个候选重新设计更容易通过的测试。

### 13.2 Rust/`toml_edit` 候选

D0 暂定 `toml_edit` 0.23.7 parse-only，并显式约束 `toml_parser = 1.0.4`、提交 `Cargo.lock` 和使用 `--locked`，把实际 parser 冻结在 TOML 1.0 语义。仅固定 `toml_edit` 不足以阻止其普通 1.x 传递依赖升级。当前 0.25.x 标注 `spec-1.1.0`，不能直接用于 `rules.toml format = 1`。

必须使用保留原始 generated text 的不可变 Document：

```rust
let document = toml_edit::Document::parse(generated_toml)?;
let table_span = inline_table.span();
let source_span = from_value.span();
let target_span = to_value.span();
```

`Item::span()`、`Value::span()`、`InlineTable::span()` 和 parse error span 均按 generated byte range 参与绑定。不得在绑定和 scope validation 前调用 `into_mut()`；该转换会 `despan()`，使节点失去原始区间。编译器不修改 Document，也不把它越过 C ABI 或保存到 RulesDocument。

Rust 候选通过条件：

1. inline table span 精确覆盖生成的 `{ ... }`。
2. `from`/`to` value span 精确覆盖复制的字符串 token。
3. BOM 和 CRLF 不改变 byte-range 语义。
4. TOML 1.0 接受/拒绝 conformance 测试稳定。
5. Android arm64 静态库、panic containment、峰值内存和 stripped 体积满足预算。

如果 Rust adapter 需要隐藏标记、`DocumentMut`、自建 TOML CST 或把 AST/span 暴露给 C++，视为该候选失败，不继续叠加 fallback。

### 13.3 C++/toml++ 候选

锁定 toml++ v3.4.0 并验证：

1. inline table `node::source()` 是否覆盖完整 `{ ... }`。
2. `from` 和 `to` value node 是否有精确 source region。
3. line/column 在 ASCII、Unicode、CRLF 和 BOM 下的计数语义。
4. 跨行原始规则折叠成单行生成文本后，RewriteMap 是否能稳定恢复。
5. `TOML_EXCEPTIONS=0` 模式下 parse error 是否保留同等位置信息。

#### 受控 fallback 原型

只有 C++ 候选 source region 不可靠时，D0 才允许验证一次内部隐藏标记原型：

```toml
{ from = "A", to = "B", __pg_internal_arrow = "<compile-nonce>:<rule-id>" }
```

- `compile-nonce` 使用每次编译生成的高熵随机值。
- `rule-id` 是单次编译递增 ID。
- decoder 只接受与当前 GeneratedRedirect 表精确匹配且只消费一次的标记。
- 用户源中任何 `__pg_internal_*` 字段都作为保留字段错误。
- 标记在构建 RulesDocument 时剥离，绝不进入 Canonical Policy。

fallback 可工作不代表 C++ 候选自动通过。正常路径必须依赖隐藏字段时，应回到 §2.3 比较 Rust 候选和严格 TOML；只有独立架构决策明确批准后才允许固化，但 D0 的优先目标是让生产实现完全删除该 fallback。

### 13.4 共同绑定不变量

首选绑定统一为：

```text
AST inline-table generated byte span
    -> exact lookup GeneratedRedirect.generated_table
    -> RuleId
```

如果整体 table span 不精确但两个 value span 精确，C++ 候选可验证 source/target 组合匹配；Rust 候选若不能提供整体 table span，则按候选失败处理，避免在新实现中复制已知 fallback 复杂度。

每个 GeneratedRedirect 必须恰好匹配一个 AST node，每个 AST generated node 必须恰好消费一个 GeneratedRedirect。重复、缺失或多重匹配属于编译器内部错误，不继续发布策略。

只使用 `redirect[5]` Node ID 不足以证明来源：该路径在 AST 构建后才存在，无法区分用户手写 inline table，也无法定位其他字段或嵌套数组中的 generated node。内部生成文本在 rewrite 与 parse 之间不会被 formatter、排序器或其他工具修改，因此 generated byte span 是最小且直接的绑定依据。

## 14. AST 作用域验证

### 14.1 验证顺序

锁定 TOML parser 成功后：

1. 先定位并绑定所有 GeneratedRedirect AST node。
2. 为每个 node 计算语义字段路径。
3. 验证路径是否精确匹配 `/apps/<package>/redirect/<index>`。
4. 报告所有 scope 错误并标记节点。
5. 普通 RulesDocumentDecoder 跳过已报告 scope 错误的节点，避免重复类型错误。

### 14.2 接受的 TOML 表达

作用域按 AST 路径判断，而不是按用户表头的表面写法判断。因此以下等价 TOML 组织方式只要最终 AST 路径相同，都可以由标准 parser 决定：

```toml
[apps."com.example.app"]
redirect = ["A" -> "B"]
```

```toml
apps."com.example.app".redirect = ["A" -> "B"]
```

产品文档仍只推荐第一种，不需要脱糖器理解二者差异。

### 14.3 Scope 错误优先

输入：

```toml
[apps."com.example.app"]
deny = ["A" -> "B"]
```

优先报告：

```text
PG-RULE-ARROW-SCOPE
`->` 只能用于 /apps/<package>/redirect 数组
```

不先报告：

```text
deny 数组元素必须是字符串
```

scope 错误更接近用户真实意图，也避免同一根因产生多条噪声诊断。

### 14.4 手写 inline table

输入：

```toml
redirect = [
    { from = "A", to = "B" },
]
```

该 AST node 没有对应 GeneratedRedirect，报告：

```text
PG-REDIRECT-SYNTAX
redirect 数组只接受 "source" -> "target"
```

不把它静默编译为同一 RedirectRule。

## 15. 诊断优先级

阶段优先级固定为：

```text
Format probe
    -> String boundary / local arrow diagnostics
    -> Standard TOML parse diagnostics
    -> Generated node scope diagnostics
    -> Rules field/type diagnostics
    -> Path and semantic diagnostics
    -> Device admission diagnostics
```

同一根因只在最早能够准确解释的位置报告一次。

### 15.1 箭头错误时不继续 parse

如果存在任一 `PG-ARROW-*` 错误：

- 可以继续流式扫描以收集不超过 `RulesLimits.max_diagnostics` 的其他独立箭头错误。
- 不应用任何 rewrite。
- 不调用标准 TOML parser。
- 不产生部分 RulesDocument。

这样不会把链式箭头转换成半截 inline table，也不会让标准 parser 覆盖更准确的领域诊断。

### 15.2 标准 TOML 错误

局部箭头全部合法后才生成标准 TOML 并调用锁定 parser。parse error 的 generated position 必须经 RewriteMap 映射到原始 SourceSpan。

默认诊断不得显示内部 `{ from, to }`。只有显式 debug 选项可以输出脱糖文本和 generated offset。

## 16. 稳定错误码

| 错误码 | 阶段 | 含义 |
|---|---|---|
| `PG-ARROW-CONTEXT` | desugar | 箭头不位于直接 value-array 元素上下文 |
| `PG-ARROW-OPERAND` | desugar | 左右操作数缺失或不是单行 TOML 字符串 |
| `PG-ARROW-CHAINED` | desugar | 出现 `"A" -> "B" -> "C"` |
| `PG-ARROW-MISSING-COMMA` | desugar | 完整规则后直接出现下一数组元素 |
| `PG-ARROW-COMMENT-INSIDE` | desugar | 注释插入 source/arrow/target 内部 |
| `PG-ARROW-STRING-BOUNDARY` | desugar | 字符串未终止，无法安全继续识别箭头 |
| `PG-RULE-ARROW-SCOPE` | AST scope | generated arrow 不在 `apps.*.redirect` |
| `PG-REDIRECT-SYNTAX` | decode | redirect 元素不是 generated arrow inline table |
| `PG-DESUGAR-INTERNAL` | internal | rewrite 重叠、generated node 未匹配或重复消费 |
| `PG-COMPILER-INTERNAL` | FFI/compiler boundary | panic 或不可恢复内部不变量失败；不产生候选策略 |

诊断示例：

```text
rules.toml:5:11: error[PG-ARROW-CONTEXT]
`->` 只能出现在数组元素中

5 | foo = "A" -> "B"
              ^^

help: redirect 规则应写在应用表的 redirect 数组中
```

```text
rules.toml:8:9: error[PG-RULE-ARROW-SCOPE]
`->` 只能用于 /apps/<package>/redirect 数组

8 | deny = ["A" -> "B"]
            ^^^^^^^^^^
```

```text
rules.toml:12:5: error[PG-REDIRECT-SYNTAX]
redirect 数组只接受 "source" -> "target"

12 |     { from = "A", to = "B" },
         ^^^^^^^^^^^^^^^^^^^^^^^^^^
```

## 17. 核心接口草案

### 17.1 输入

```text
SourceBuffer {
    file_name: borrowed UTF-8 name
    bytes: borrowed raw bytes
    line_index: borrowed LineIndex
}

DesugarOptions {
    format_version: u32
    limits: borrowed RulesLimits
}
```

SourceBuffer 在整个 parse/decode 生命周期内保持有效。

### 17.2 输出

```text
DesugaredSource {
    generated_storage: optional owned bytes
    parser_input: borrowed original bytes or generated_storage
    generated_line_index: LineIndex
    rewrite_map: bounded RewriteSegment[]
    redirects: bounded GeneratedRedirect[]
    diagnostics: bounded Diagnostic[]
}

DesugarRulesToml(source, options) -> DesugaredSource
```

如果 `diagnostics` 包含 error，`parser_input` 不得交给标准 TOML parser。

### 17.3 纯函数边界

`DesugarRulesToml()`：

- 不读写文件。
- 不读取设备 capability。
- 不修改全局状态。
- 不记录 wall-clock 时间戳。
- 对相同输入和 limits 产生相同结果。

隐藏标记 nonce 只存在于 C++ D0 fallback 原型，由测试调用方显式注入；任何选定生产实现不得因为随机 nonce 破坏确定性编译。

### 17.4 Rust/C ABI 边界

若 D0 选择 Rust，以上脱糖接口只在 crate 内部使用，不单独导出。唯一跨语言入口覆盖完整规则编译：

```text
pg_rules_compile(
    source_ptr,
    source_len,
    compile_options,
    optional immutable admission snapshot,
    out_result_handle
) -> stable status code
```

result handle 只通过 accessor 暴露已验证 policy bytes、固定宽度 generation/requirements/admission 字段和有界结构化诊断，并由 `pg_rules_result_free()` 释放。AST、SourceBuffer 借用、DesugaredSource、RewriteMap、GeneratedRedirect、RulesDocument 和 Canonical Policy 不得越过 C ABI。

首版 ABI 规模很小，使用手写版本化 C 头、Rust `#[repr(C)]` 和双端 layout 测试，不默认引入 `cbindgen`。自动生成头文件只有在接口数量真实增长、手工同步已产生缺陷时再评估。

每个 `extern "C"` 入口必须在 Rust 内部执行 `catch_unwind`，把 unwind panic 转成 `PG-COMPILER-INTERNAL`；不能让 panic 穿越 C ABI。该保护只对 `panic = "unwind"` 有效，不能捕获 OOM abort、stack overflow、信号崩溃或 `panic = "abort"`。返回任何内部错误时，daemon 不发布候选并继续使用上一份有效 `policy.bin`。

## 18. 安全与资源限制

脱糖器共享规则编译器的 `RulesLimits`，至少限制：

- 源文件最大字节数。
- 最大容器嵌套深度。
- 最大箭头候选和 Rewrite 数量。
- 单字符串 token 最大字节数。
- RewriteMap segment 数量。
- 最大诊断数量。
- 生成文本最大字节数。

实现要求：

- 所有偏移加法检查溢出。
- Rust release profile 启用 `overflow-checks = true`；用户输入派生的 offset/length 仍必须显式使用 checked arithmetic，不能只依赖 profile。
- 不使用递归扫描容器。
- 容器栈使用有界 vector/small-vector。
- 合成文本大小在分配前计算并验证。
- 任一失败都不产生部分可发布策略。
- 不把用户字符串拼接为 shell 命令或格式字符串。
- Rust 自有扫描、rewrite 和 encoder 模块禁止 `unsafe`；第三方 crate 的内部 `unsafe` 通过版本锁定、上游测试、fuzz 和依赖审核管理，不能宣称“使用 Rust 即不存在内存安全风险”。

## 19. 性能设计

### 19.1 复杂度

设：

- N：源文件字节数。
- R：箭头规则数。
- A：TOML AST 节点数。

各阶段：

| 阶段 | 时间 | 额外内存 |
|---|---:|---:|
| Format probe | O(文件头)，最坏 O(N) | O(1) |
| Streaming lexer | O(N) | O(R + depth) |
| Rewrite emit | O(N + R) | O(N + R) 生成文本 |
| strict TOML parse | O(N) 期望 | 由选定 parser AST 决定 |
| Generated scope validation | O(A + R) | O(R) |
| RewriteMap 单次查询 | O(log R) | O(1) |

脱糖器本身不会执行路径排序和冲突检测；完整规则编译仍为 O(N + Rules log Rules)。

### 19.2 CPU 与发布预算分离

CPU 编译预算不包括持久化：

```text
format probe
lex
rewrite
toml parse
decode
normalize
conflict
canonicalize
admission
encode
verify
```

发布预算单独统计：

```text
write temp
fsync file
rename
fsync directory
status publish
```

TOML AST 分配通常是 CPU 主要候选；`toml_edit` 的 trivia/span 保留可能增加内存，toml++ 的 AST/source-region 转换也有自身成本。低端闪存上的 fsync 可能是端到端主要耗时，不得在没有目标设备数据时固定排序或预设 Rust/C++ 哪个更快。

### 19.3 建议性能预算

| 场景 | CPU 编译目标 | 峰值内存目标 |
|---|---:|---:|
| ≤64 KiB、≤256 条规则 | P95 < 10 ms | < 16 MiB |
| ≤256 KiB、≤2,000 条规则 | < 50 ms | < 24 MiB |
| ≤1 MiB、≤4,096 条规则 | < 100 ms | < 32 MiB |

预算需在至少一台低端/旧内核 Android 设备和 Host CI 上测量后冻结。D0 两个候选必须使用相同编译模式、输入集合、预热策略和统计方法；不得把 C++ parser-only 数字与 Rust 端到端数字直接比较。

若选择 Rust，C ABI 不复制输入源；policy bytes 和诊断在 result handle 内只生成一次。`toml_edit::Document`、生成文本和 RewriteMap 的共存峰值必须包含在内存预算中。stripped daemon/CLI 增量体积和 Rust 静态库体积单独记录，但最硬约束仍是 Zygisk ELF 零依赖。

### 19.4 发布优化边界

- validate-only 不写 `policy.bin`。
- source digest 变化但 Canonical Policy content generation 未变化时，只更新状态，不重写二进制、不 reload。
- 文件监控使用单 reconcile worker 合并重复保存。
- 默认仍保持临时文件、校验、原子 rename、文件 fsync 和目录 fsync。
- `policy.bin` 虽可重建，但它参与下一次启动的快速、安全加载；降低持久化强度必须有独立 ADR 和真机故障测试，不能作为首版默认优化。

### 19.5 性能指标

至少记录：

```text
format_probe_ns
arrow_lex_ns
rewrite_emit_ns
toml_parse_ns
scope_validate_ns
decode_ns
normalize_ns
conflict_ns
canonicalize_ns
admission_ns
encode_ns
verify_ns
publish_ns
source_bytes
generated_bytes
arrow_count
rewrite_segment_count
peak_memory_bytes
compiler_backend
parser_version
policy_blob_bytes
c_abi_total_ns        # 仅 Rust+C ABI 候选
```

### 19.6 路径隔离

脱糖器只在以下控制面操作中运行：

- daemon 观察到 `rules.toml` 新 source digest。
- `pathguardctl validate/compile`。
- Manager 保存或显式请求校验。

它不进入 Zygisk specialization、应用启动、mount transaction、Provider hook 或文件访问路径。构建系统和链接测试必须从二进制依赖层证明这一点，而不是只依赖代码约定。

性能优化分两层：

- `source_digest` 未变化：跳过整个编译管线。
- source digest 变化但 Canonical Policy content generation 未变化：完成校验和状态更新，但跳过 `policy.bin` 重写与运行时 reload。

Manager 保存后的校验反馈仍是用户可感知延迟，因此 CPU 预算不能因为它属于冷路径而取消；只是该延迟与应用启动热路径完全隔离。

## 20. 测试策略

### 20.1 基础合法输入

覆盖：

```toml
redirect = ["A" -> "B"]
redirect = ['A' -> 'B']
redirect = ["A"->"B", "C" -> "D",]
redirect = [
    "A"
        -> "B",
]
```

断言：

- 脱糖文本可由两个 D0 候选解析，并最终由选定 parser 解析。
- AST 生成两字段 inline table。
- source/target 原始字节未改变。
- GeneratedRedirect span 正确。

### 20.2 字符串与注释边界

至少覆盖：

```toml
"A -> B" -> "C"
'A -> B' -> 'C'
"A\" -> still string" -> "B"
"A\\" -> "B"
"""A -> B"""
'''A -> B'''
# "A" -> "B"
"A" # -> "B"
```

多行字符串中的箭头不得产生候选。

### 20.3 局部上下文

| 输入 | 预期 |
|---|---|
| `foo = "A" -> "B"` | `PG-ARROW-CONTEXT` |
| `foo = { bar = "A" -> "B" }` | `PG-ARROW-CONTEXT` |
| `["A" -> "B"]` | `PG-ARROW-CONTEXT`，table header |
| `redirect = ["A" ->]` | `PG-ARROW-OPERAND` |
| `redirect = [-> "B"]` | `PG-ARROW-OPERAND` |
| `redirect = ["A" -> "B" -> "C"]` | `PG-ARROW-CHAINED` |
| `redirect = ["A" -> "B" "C" -> "D"]` | `PG-ARROW-MISSING-COMMA` |
| `"A" # comment` 后接箭头 | `PG-ARROW-COMMENT-INSIDE` |
| 箭头后注释再接 target | `PG-ARROW-COMMENT-INSIDE` |

### 20.4 Scope

```toml
deny = ["A" -> "B"]
processes = ["a" -> "b"]
redirect = ["A" -> "B"] # top-level
foo = [["A" -> "B"]]
```

局部语法合法的候选完成脱糖，AST 阶段统一报告 `PG-RULE-ARROW-SCOPE`。

### 20.5 手写 inline table

```toml
redirect = [
    { from = "A", to = "B" },
]
```

以及混合输入：

```toml
redirect = [
    "A" -> "B",
    { from = "C", to = "D" },
]
```

未生成元素报告 `PG-REDIRECT-SYNTAX`。

### 20.6 标准 TOML 错误

合法箭头旁存在：

- 缺少数组 `]`。
- 重复键。
- 非法 escape。
- 非法 UTF-8。
- 非法 inline table。
- 重复应用表。

断言两个候选的 parse error 经 RewriteMap 后落在同一原始 byte span。

### 20.7 Source map golden

每个 golden 至少固定：

```text
file
original byte begin/end
begin/end line
begin/end display column
error code
primary message
related spans
```

覆盖：

- LF 与 CRLF。
- UTF-8 BOM。
- ASCII 和多字节 Unicode。
- 同行和跨行箭头。
- 多条 rewrite 之后的普通 TOML parse error。
- parser error 落在 copied、synthetic-rule 和 synthetic-arrow segment。

### 20.8 属性测试

属性一：无外部箭头恒等。

```text
input without external arrow
    => parser_input aliases original bytes
    => rewrite_map empty/identity
    => redirects empty
```

属性二：合法箭头模板脱糖后可解析。

```text
valid generated PathGuard arrow document
    => Desugar success
    => locked strict TOML parse success
```

属性三：操作数字符串字节保持。

```text
raw source/target token bytes before rewrite
    == raw value token bytes in generated TOML
```

属性四：生成节点一一消费。

```text
GeneratedRedirect count
    == bound generated AST node count
```

### 20.9 Fuzz

分别 fuzz：

1. TOML 字符串边界扫描器。
2. 容器栈和箭头候选状态机。
3. RewriteMap offset 映射。
4. 完整 `Desugar -> locked TOML parser -> scope validate` 管线；D0 期间两个 adapter 使用同一 fuzz corpus。

不变量：

- 不越界、不死循环、不出现整数溢出。
- 任意输入不会产生重叠 rewrite。
- 任意成功输出不残留字符串外部 `->`。
- 任何 error 输出不得进入 PolicyEncoder。
- 诊断 span 必须位于原始 SourceBuffer 范围内。

### 20.10 畸形前缀组合测试

完整管线 fuzz 必须专门生成：

```text
MalformedTomlPrefix + ValidRedirectSuffix
```

畸形前缀至少包括：

- 未闭合或多余的 `[`、`]`、`{`、`}`。
- 非法 table header 和 array-of-tables header。
- 无效 key/value 标点组合。
- 非法 token 后换行。
- 未终止单行/多行字符串和注释边界组合。

合法后缀包含一段标准应用表和 redirect 数组。测试目的不是要求扫描器从所有不可恢复的词法错误中“重新同步”，而是验证：

1. 前文畸形内容不会产生可发布但语义错误的策略。
2. frame 栈漂移不会导致 GeneratedRedirect 与错误 AST node 静默绑定。
3. 主诊断应指向畸形前缀或实际箭头位置，不得越界或漂移到无关后续行。
4. 未终止字符串合法地吞没后续文本时，应报告字符串边界错误，而不是假装识别后缀箭头。
5. 任何 generated node mismatch 都以 `PG-DESUGAR-INTERNAL` 终止，不降级为成功结果。

### 20.11 D0 adapter、C ABI 与 binary golden

同一测试驱动同时运行 C++/toml++ 与 Rust/`toml_edit` adapter，比较：

- generated table/source/target byte span。
- parser error 映射后的原始 byte span、错误码和关联位置。
- scope validator 对合法箭头、错误作用域和手写 inline table 的结果。
- TOML 1.0 接受/拒绝集合；Rust lockfile 不得因升级接受 TOML 1.1-only 输入。
- 无箭头、典型、大型和极限输入的 CPU、峰值内存与生成文本大小。

Rust vertical slice 还必须覆盖：

- 固定输入生成当前 207-byte `policy.bin format v5` golden，逐字节比较。
- 现有 C++ `DecodePolicy()` 读取 Rust 输出并验证 checksum、content generation、排序和字段边界。
- C ABI 的 null/length 组合、非法 UTF-8、超限输入、未知 ABI/枚举、result accessor 和唯一释放路径。
- C 与 Rust 对所有公开 POD 的 `sizeof`、`alignof`、字段 offset 和枚举宽度一致。
- 在编译入口内部注入 unwind panic，返回 `PG-COMPILER-INTERNAL`，不产生 policy bytes；随后再次编译仍可成功。
- Android arm64 静态链接后，`pathguard_zygisk` ELF 不出现 Rust、`toml_edit`、toml++ 或规则诊断依赖。

这些测试是 D0 决策输入，不是选定实现后的补测。任何候选无法运行同一外部断言时，应修正 adapter 或判定候选失败，不能削弱 golden。

## 21. 实施分解

### Phase D0：依赖验证

- 先冻结 binder-neutral source-map/generated-node golden 语料和统一断言。
- 冻结 TOML 1.0 conformance 子集和 parser 拒绝集，防止依赖更新扩大 format 1 语法。
- 实现最小 C++/toml++ adapter，验证 table/value source region、line/column、Unicode、CRLF、BOM 和无异常错误位置。
- 实现最小 Rust/`toml_edit` adapter，验证不可变 `Document` 的 table/value/error byte span，并用回归测试证明 `DocumentMut` 不得进入 binder。
- Rust 候选使用 `toml_edit` 0.23.7 parse-only；提交候选 `Cargo.lock`，记录实际 TOML 1.0 parser、Rust MSRV、许可证和依赖树。0.25.x `spec-1.1.0` 不进入 format 1 spike。
- 两个 adapter 使用同一 golden 与 fuzz corpus；仅在 C++ source region 失败时制作隐藏标记原型，Rust 候选不增加第二套 fallback。
- 建立最小完整 Rust compiler vertical slice：固定规则输入经过 decode/canonicalize/encode 生成当前 207-byte `policy.bin format v5` golden，并由现有 C++ `DecodePolicy()` 独立读取。
- 建立最小 C ABI harness，验证 source bytes/length、opaque result/free、稳定错误码、未知 ABI/枚举拒绝、panic 转换和重复调用；不暴露 AST、RewriteMap 或 IR。
- 在 Host 和 Android arm64 测量 parser/完整 slice 的时间、峰值内存、stripped 体积和构建时间，并从最终 ELF 依赖证明未进入 Zygisk。
- 按 §2.3 输出明确的联合 Go/No-Go：选择 Rust 完整规则编译器、选择 C++ 完整规则编译器，或退回严格 TOML。
- 冻结箭头错误码和 RulesLimits。
- 导入必要的 TOML 官方字符串边界测试样例。

D0 没有通过前不得开始 D1 生产实现。最终决议必须删除未选中的 adapter、parser 和 fallback 原型；fallback 能够工作不等同于箭头方案或 C++ 候选自动获得 Go 结论。

D0 执行前置：

- 当前开发机已具备 Rust 1.97.1、`aarch64-linux-android`/`armv7-linux-androideabi` targets 和 cargo-ndk 4.1.2，不需要在 spike 中执行全局安装。
- C++ 与 Rust Android 样本统一使用现有 native 构建基线：NDK r27d（27.3.13750724）、API 31、首个目标 `arm64-v8a`。构建脚本必须打印并校验 NDK revision，不能让 cargo-ndk 自动选择另一套 SDK NDK 后再比较结果。
- D0 可以临时使用当前 Rust toolchain。为保证 spike 可复跑，候选 manifest/lockfile 作为隔离的 D0 artifact 保存；只有 Rust 候选获得 Go 结论后才把它们提升为正式 `pathguard_rules_compiler` manifest/lockfile，并提交 `rust-toolchain.toml` 和生产构建入口。未选中的 artifact 随 adapter 一起删除。
- 依赖下载完成后，Host golden、fuzz seed 和 Android release 构建必须支持 `--locked`；正式 CI 不允许静默更新依赖。
- D0 报告必须记录完整命令、compiler/parser/NDK 版本、输入摘要、构建模式和原始测量数据，确保两候选可复跑。

### Phase D1：词法与局部上下文

- 实现 FormatProbe。
- 实现字符串/注释边界状态机。
- 实现 value array、inline table、table header 浅层 frame 栈。
- 实现流式候选状态机和 `PG-ARROW-*` 诊断。
- 完成 lexer/state-machine fuzz。
- 若选择 Rust，以上模块先放在单个 `pathguard_rules_compiler` crate 内，不按状态机/RewriteMap/decoder 拆 crate。

### Phase D2：Rewrite 与位置映射

- 实现 ArrowRewrite 非重叠验证。
- 实现单次标准 TOML 输出。
- 实现 RewriteMap、原始/生成 LineIndex 和位置查询。
- 完成 LF/CRLF/BOM/Unicode golden。

### Phase D3：锁定 TOML parser 与 AST scope

- 接入 D0 选定的唯一 parser；Rust 路径使用不可变 `toml_edit::Document`，C++ 路径使用无异常 toml++。
- 实现 generated node 绑定和一一消费。
- 实现 AST 字段路径验证。
- 实现手写 inline table 拒绝。
- 实现 scope 优先和派生类型诊断抑制。

### Phase D4：集成与性能

- 接入 RulesDocumentDecoder。
- 完成从 source bytes 到 verified PolicyBlob 的单一编译入口；若选择 Rust，C ABI 只包住该完整入口。
- 若选择 Rust，daemon 在发布前用现有 C++ `DecodePolicy()` 独立验证返回字节；失败转换为 `PG-COMPILER-INTERNAL`，不发布候选。
- 增加阶段性能指标。
- 在 Host、低端 Android 和目标真机运行预算测试。
- 验证无箭头快路径和 content-generation 不变时跳过发布。
- 若选择 Rust，验证 `catch_unwind` 只处理 unwind panic，并注入 panic 证明 daemon 保留上一份有效策略。

## 22. 审核意见取舍

| 建议 | 决策 | 原因 |
|---|---|---|
| 区分“能够安全实现”和“值得投入” | 采纳 | D0 同时承担技术验证和箭头语法 Go/No-Go 决策 |
| 使用 Streaming Lexer | 采纳 | 箭头判断局部化，不需要完整 TokenStream |
| RewriteMap 简化为有序 offset segments | 采纳 | 通用 parser 位置映射只需要分段和二分查找 |
| 完全删除 GeneratedRedirect 的操作数 span | 不采纳 | 路径和冲突诊断仍需分别指向 source/target 原始位置 |
| 允许用户手写 `{ from, to }` | v1 不采纳 | 会形成双语法、扩大 fmt/Manager/测试面；高级属性使用独立命名空间 |
| 只使用 `redirect[index]` GeneratedNodeID | 不采纳 | AST 前不存在该路径，且无法定位其他作用域中的 generated node |
| Rewrite 直接生成完整 TokenStream | 首版不采纳 | 锁定 parser 输入是文本，核心编译器不做 formatter；违反 YAGNI |
| 增加局部数组元素上下文检查 | 采纳 | 更早发现 context、missing comma 和 chained arrow，且不解析表路径 |
| 局部箭头错误优先于 TOML parse | 采纳 | 避免半转换文本产生误导性标准 TOML 错误 |
| 提前验证 toml++ source region | 采纳 | 作为 C++ 候选，必须与 Rust byte-span adapter 使用同一断言 |
| 将 Rust/`toml_edit` 纳入 D0 | 采纳 | 该组件完全位于控制面，byte span 和文本安全与需求高度匹配 |
| 只用 Rust 实现脱糖器 | 不采纳 | 会在流水线中间增加 FFI，无法消除 C++ parser/source-region 风险 |
| 整条规则编译链作为 Rust 边界 | 条件采纳 | D0 通过后采用；C ABI 只暴露完整编译结果，不暴露 AST/span/IR |
| 直接使用最新版 `toml_edit` | 不采纳 | 0.25.x 对应 TOML 1.1，不能偷偷改变 format 1 的 TOML 1.0 语义 |
| 用 `DocumentMut` 做 generated binding | 不采纳 | `into_mut()` 会 despan，破坏来源绑定所需区间 |
| 用 `catch_unwind` 作为完整崩溃隔离 | 不采纳 | 只捕获 unwind panic，不能捕获 abort/OOM/stack overflow/signal |
| 首版使用 `cbindgen` | 暂不采纳 | 单一入口和少量 accessor 用手写版本化头加 layout 测试更简单；接口真实扩张后再评估 |
| source region 失败时设置 kill criterion | 采纳 | fallback 可用不代表投入产出仍然成立，必须重新比较严格 TOML |
| primary/fallback 共用一套 golden 语料 | 采纳 | 将测试基础设施与不确定的 binder 结论解耦 |
| 增加畸形前缀加合法 redirect 后缀 fuzz | 采纳 | 验证 frame 漂移只影响诊断、不产生静默错误策略 |
| RewriteMap 查询只留在诊断分支 | 采纳 | 成功路径直接使用 generated span 索引，避免无意义 O(log R) 查询 |
| 根据 Manager/手工编辑实际占比复审箭头价值 | 采纳 | 可扩展性已冻结，但用户价值可能随编辑入口变化 |
| 降低 `policy.bin` fsync 强度 | 暂不采纳 | 先通过跳过无语义变化发布优化；耐久性调整需要独立证据和 ADR |

## 23. 拒绝方案

- 对全部文本执行 `ReplaceAll("->", ...)`。
- 用正则表达式解析 TOML 字符串和注释。
- 把整个 `source -> target` 放入一个字符串后二次解析。
- 在脱糖器中解析 `[apps."package"]` 表路径。
- 把任意位置的 `string -> string` 都转换成 inline table。
- 发现链式或缺失操作数后继续生成部分重写文本。
- 在首版维护完整 token/trivia/CST 供未来 formatter 使用。
- 同时接受箭头和手写 `{ from, to }` 作为普通 redirect 输入。
- 为未来未知语法糖设计通用运算符注册系统。
- 只把脱糖器做成 Rust 静态库，再把生成文本、RewriteMap 或 AST 交回 C++ parser。
- 在生产中同时保留 Rust/`toml_edit` 和 C++/toml++ 两套规则编译器。
- 在 generated node 绑定前把 `toml_edit::Document` 转成 `DocumentMut`。
- 不升级规则格式版本就让 Cargo 依赖启用 TOML 1.1 语法。

## 24. 完成定义

满足以下条件后，箭头脱糖器才算完成：

1. 字符串和注释中的 `->` 不产生 ArrowCandidate。
2. 只转换直接 value-array 元素中的单行 `string -> string`。
3. table header、普通键值和 inline table 字段中的箭头得到稳定 context 诊断。
4. 链式箭头、内部注释、缺失操作数和缺失逗号在标准 TOML parse 前失败。
5. 合法跨行箭头生成单行严格 TOML inline table。
6. 无箭头输入走零 rewrite 快路径。
7. 所有成功脱糖输出都能由锁定版本的唯一生产 parser 解析。
8. generated node 只能出现在 `/apps/<package>/redirect/<index>`。
9. 用户手写 `{ from, to }` 被稳定拒绝。
10. parser 和语义诊断都准确映射回原始 rules.toml byte span。
11. Unicode、CRLF、BOM 和多次 rewrite 后的位置 golden 全部通过。
12. 两个 parser adapter 使用同一 source-region/byte-span 自动测试，并已冻结唯一生产实现和 fallback 删除决策。
13. lexer、RewriteMap 和完整管线 fuzz 不存在越界、死循环或重叠 rewrite。
14. 典型、大型和极限配置满足已冻结 CPU/内存预算。
15. 选定 parser、Rust runtime（如采用）、脱糖器和诊断代码不会链接进入 Zygisk 数据面。
16. D0 已形成明确 Go/No-Go 记录，证明箭头体验收益仍值得其实现与测试成本。
17. `MalformedTomlPrefix + ValidRedirectSuffix` 组合 fuzz 不会产生静默错误策略或 generated node 误绑定。
18. 无诊断成功路径不调用通用 RewriteMap generated-to-original 查询。
19. TOML 1.0 conformance 和拒绝集在锁定依赖更新后仍通过；format 1 不接受 TOML 1.1 扩展。
20. 若选择 Rust，generated binding 全程使用不可变 `toml_edit::Document`，C ABI 不暴露 AST/span/IR，panic 和内存所有权测试全部通过。
21. 选定完整规则编译器对固定输入生成当前 207-byte `policy.bin` golden，并由现有 C++ reader 独立验证。
22. 若选择 Rust，每次候选发布前都由 C++ `DecodePolicy()` 验证格式、checksum、generation、排序和边界，失败时不发布。

## 25. 最终推荐流程

```text
rules.toml
    -> format probe
    -> streaming TOML boundary lexer
    -> direct value-array arrow validation
    -> all-or-nothing rewrite emit
    -> strict TOML + RewriteMap + GeneratedRedirect
    -> locked strict TOML parse
    -> generated node binding
    -> apps.*.redirect scope validation
    -> RulesDocument decode
    -> semantic compile
    -> Canonical Policy IR
    -> verified PolicyBlob
```

该方案只为用户真正需要的 `->` 增加最小词法扩展。它不重新实现 TOML，不为未来 formatter 提前保存 PathGuard 自建完整 token 流，也不开放第二套 redirect 语法；D0 只选择一个完整编译器和一个 parser。若选择 Rust，`toml_edit` 的不可变 Document 仅作为单次 parse/decode 实现细节，整个组件通过 verified PolicyBlob 与 C++ 运行时解耦。

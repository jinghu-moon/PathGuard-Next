# Hide H0.4 SUSFS audit and H0 decision: Xiaomi alioth

## 1. H0.4 设备结果

- [ ] Pass
- [ ] Conditional
- [ ] Kill
- [x] Unsupported：当前设备没有 SUSFS/KernelSU backend。

只读检查未发现：

```text
ksu_susfs / sus_su
/data/adb/ksu
/data/adb/susfs*
/data/adb/modules/*susfs*
/sys/module/susfs
/proc/kallsyms 中的 susfs/sus_path 符号
dmesg 中的 SUSFS 初始化记录
```

设备运行 Magisk 30.6 和厂商 4.19 内核，不满足“已经使用受支持 SUSFS 2.2 内核”的
H0.4 前提。因此不执行 `add_sus_path`，不创建 `..5.u.S`，也不把不可运行的黑盒矩阵
伪装成失败结果。

## 2. ABI 结论

此前对 SUSFS 2.2 与前端的源码审计继续成立：

- `add_sus_path` 输入是路径，不携带 package、UID list、mount namespace handle 或
  PathGuard policy generation；
- 生效依赖 SUSFS/KernelSU 自身的 task `TIF_PROC_UMOUNTED` 分类；
- 同一个 inode 标记会影响整类符合条件的 App，不能表达“只对 LocalSend 隐藏”；
- MediaProvider 自身和 Provider/Picker/SAF 访问面仍需独立能力；
- BRENE/susfs4ksu-module 只编排同一 ABI，不增加 per-app isolation。

所以即使换到已有 SUSFS 的设备，当前 ABI 也只能作为机制对照，不能直接编写 PathGuard
生产 adapter。解除 blocked 的条件是上游提供可核验、版本化、fail-closed 的
per-namespace/per-policy ABI，并通过 H0.1 全矩阵。

## 3. H0.5 最后方案准入

H0.2 与 H0.3 已淘汰 stock MediaProvider 和稳定 LKM 路线，H0.4 也没有可用 per-app
ABI；但这只满足内核补丁准入的一部分。当前仍缺少：

- 与设备 ROM 精确对应的 kernel source commit；
- 可复现原厂 kernel 的 defconfig、clang/toolchain 和构建记录；
- 已验证可恢复的 boot image 与失败回滚流程；
- 设备白名单、OTA 跟进和长期维护范围的产品批准。

因此 H0.5 状态为 **Blocked / Not started**。不会在未知源码基线上写或刷入内核补丁。

## 4. H0.6 最终决策

本次 H0 选择决策门第 4 项：

```text
mediaprovider_fuse: Kill
lkm_vfs: Unsupported / Blocked
susfs_adapter: Unsupported / Blocked
kernel_patch_vfs: Blocked by prerequisites
final: hide unsupported; keep deny
```

这不是 `deny` 的功能缺陷，也不允许把 `deny` 重命名成 `hide`。当前产品继续提供：

- `deny`：空目录 bind mount，阻止访问但目录名/挂载痕迹可观察；
- `redirect`：应用私有 mount namespace 中的路径重定向；
- `hide`：不进入 schema、`policy.bin`、Manager 或生产数据面。

未来只有出现新的稳定 stock-kernel 接口、SUSFS per-namespace ABI，或项目补齐最后方案
的完整内核构建/回滚基线时，才重开 H0 对应阶段；现有证据无需重做。

# Hide H0.1 all-files and selector baseline: Xiaomi alioth

## 1. 结论

本次完成 `dev.pathguard.hideprobe` 在 `READ_MEDIA_IMAGES` 与
`MANAGE_EXTERNAL_STORAGE` 均已授予时的 app-domain 基线，并完成系统 Photo Picker、
SAF 单文件、Pictures tree 和 DCIM tree 四个选择器入口的真实交互验证。

结果证明：all-files 权限不会让 App 获得对 `/mnt/runtime/*`、`/mnt/user/*` 或
`/data/media/*` alias 的额外访问；目标通过 canonical、`/sdcard`、
`/storage/self/primary`、MediaStore、Photo Picker 和 SAF 仍然可见。H0.1 的基线
oracle 已冻结，可以进入 H0.2；这仍然不是 `hide` 后端通过证明。

## 4. All-files 对 direct VFS 的影响

两个目标为：

```text
/storage/emulated/0/Pictures/Nagram
/storage/emulated/0/DCIM/Screenshots
```

授予 all-files 后，Java `File`、NIO、JNI/libc 和 raw syscall 的结果与普通媒体权限
基线相同：

- canonical、`/sdcard`、`/storage/self/primary` 上目标与后代可见且可打开；
- parent 的 libc `readdir` 和 raw `getdents64` 可枚举目标 basename；
- `/mnt/user/*`、`/mnt/runtime/*` 和 `/data/media/*` 仍由平台权限返回 `EACCES`；
- `openat2` 与 `faccessat2` 仍为内核 `ENOSYS`；
- 私有沙箱 mutation 完成且无残留；
- `/proc/self/mountinfo`、`mounts`、`mountstats` 未产生变化。

因此不能把 all-files 当作“覆盖全部 storage alias”的测试捷径。生产回归必须以目标
App 实际可达的 canonical 与公开 alias 为主，并单独保留内部 alias 的平台权限基线。

## 5. MediaStore 与选择器

| 访问面 | 结果 |
|---|---|
| MediaStore `Pictures/Nagram/` | legacy 2、Bundle 2、已知 URI 可打开 |
| MediaStore `DCIM/Screenshots/` | legacy 18、Bundle 18、已知 URI 可打开 |
| Photo Picker | 可启动；选中 Screenshots 图片后 URI 可 query/open |
| SAF image | 可启动；同一 Screenshots 图片 URI 可 query/open |
| SAF Pictures tree | 34 个直属子项；`Nagram` 命中 1 |
| SAF DCIM tree | 18 个直属子项；`Screenshots` 命中 1 |
| CloudMediaProvider | 当前设备未配置，记为 `Unsupported` |

Photo Picker 的“影集”页显示“相机、屏幕截图、下载内容”。`Screenshots` 影集和图片
完整可见；`Nagram` 没有作为独立影集出现，但这不能解释为隐藏成功，因为 MediaStore
仍返回其中 2 张图片，SAF Pictures tree 也直接枚举到该目录。

这组结果冻结了 Provider/selector 的独立 oracle：未来 direct-VFS backend 即使通过，
也不得据此宣称 `hide.media_query`、`hide.photo_picker` 或 `hide.saf` 已通过。

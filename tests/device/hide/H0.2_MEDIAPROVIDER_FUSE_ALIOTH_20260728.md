# Hide H0.2 MediaProvider FUSE spike: Xiaomi alioth

## 1. 决策

- [ ] Pass
- [ ] Conditional
- [x] Kill：stock-kernel MediaProvider 注入路线不进入产品代码。
- [ ] Unsupported

本阶段在写入或注入任何 MediaProvider Hook 之前已经命中既定 kill criteria：目标目录
的 direct lookup 没有稳定、公开且同时携带完整路径与请求 UID 的接入点；正确处理
per-UID dentry cache 又必须进入 MediaProvider 私有静态实现或全局关闭缓存。

因此不安装实验模块、不重启 MediaProvider，也不承担“先让系统 Provider 崩一次再看”
的设备风险。结论是 **stock-kernel exact hide unsupported**，不是退回 Java/ART/PLT Hook
继续叠加兼容层。

## 2. 设备实现

| 字段 | 结果 |
|---|---|
| Package | `com.android.providers.media.module` |
| APEX | `/apex/com.android.mediaprovider` |
| version | `versionName=13`、`versionCode=33` |
| FUSE service | `com.android.providers.media.fuse.ExternalStorageServiceImpl` |
| 进程 | `com.android.providers.media.module` / `mediaprovider_app` |
| APK native 库 | `libfuse.so`、`libfuse_jni.so` |
| App storage mount | `/dev/fuse`，device `0:109`，shared master `47` |
| MediaProvider backing view | `/mnt/pass_through/0/emulated` / `sdcardfs` |
| passthrough | `persist.sys.fuse.passthrough.enable=true` |
| FUSE BPF | 当前 4.19 kernel 没有 `/sys/fs/fuse/features/fuse_bpf` |

`dev.pathguard.hideprobe` 的 private namespace 中 `/storage/emulated` 和
`/mnt/user/0/emulated` 虽有不同 mount ID，但都指向 device `0:109`、shared master `47`。
namespace 克隆没有为每个 App 创建独立 FUSE superblock/dentry cache。

## 3. 二进制证据

设备 APK SHA-256：

```text
F8F71EAEDD78A1BB0C3BB3D81405F2529221FE6358CA5FE4CE74A5C3853CA9ED  MediaProvider.apk
```

Android 13 的 `libfuse_jni.so` 动态导出了：

```text
MediaProviderWrapper::FileLookup(path, uid, tid)
MediaProviderWrapper::GetDirectoryEntries(uid, path, DIR*)
MediaProviderWrapper::ShouldAllowLookup(uid, user_id)
```

三者在该 ELF 中均有 `R_AARCH64_JUMP_SLOT`。这证明单机上可以做 GOT/PLT
重定向，但不证明存在可交付 ABI。关键限制是：

1. `validate_node_path()` 先执行 `lstat()`；若对象是目录，直接返回成功，根本不调用
   `FileLookup()`。所以 Hook `FileLookup()` 不能隐藏本项目的目录规则。
2. `GetDirectoryEntries()` 只影响 `readdir`，不能让已知路径 direct lookup 返回
   `ENOENT`。
3. 真正同时掌握 `parent + name + req->ctx.uid + fuse_entry_param` 的
   `do_lookup()`、`make_node_entry()` 和 `do_readdir_common()` 是同一 DSO 内的
   `static` 实现，不在设备 dynsym 中。
4. Hook 通用 `fuse_reply_entry()` 只能看到 reply 与 inode，缺少稳定的 parent/name
   语义；继续读取 MediaProvider 私有 node/fuse 布局仍然回到私有 ABI。

## 4. Per-UID cache 阻断

AOSP Android 12、13、14、15、16 release 分支均保持以下结构：

- 目录在 `FileLookup()` 前提前返回；
- `do_lookup()` 与 `do_readdir_common()` 为静态内部函数；
- positive lookup 设置 `entry_timeout`，attr 通常长期缓存；
- FUSE BPF 路径会绕过用户态 daemon，当前只特判 `Android/data|obb`。

核验 commit：

| 分支 | commit |
|---|---|
| `android12-release` | `bb1f5059b0444a4c3e7d0177be52f175bb9be56a` |
| `android13-release` | `18a623a6bef8888e81eac99b34ff1bd1b6ce7d9d` |
| `android14-release` | `4bc56dd095fb4ee2f754905316aa1ff8515b5ffa` |
| `android15-release` | `1dd3a03eae6dbf5c979e946c0ebae9b7196c23d0` |
| `android16-release` | `d3bb9ac8e6daab448635eaa30e85e2e8d8cbad8e` |

同一 dentry 对目标 UID 应为 `ENOENT`、对非目标 UID 应为 positive。只在用户态 lookup
回调按 UID 返回不同结果并不充分：非目标 App 可先建立 positive dentry，目标 App 随后
在 VFS cache 命中而不进入 FUSE lookup。要保证正确，只能：

- 对候选路径的 lookup/attr 在所有 UID 下强制零缓存，并准确失效已有 dentry；或
- 为目标 App 提供独立 FUSE superblock/view。

前者必须改写 `fuse_entry_param` 的内部构造路径，且扩大所有访问者的热路径开销；后者
已超出“接入现有 stock MediaProvider”的范围。全局关闭共享存储 dentry cache 直接命中
H0.2 kill criterion。

## 5. 参考项目对照

Storage Redirect X 的 `fuse_fixer` 需要从 MediaProvider APK ZIP 恢复完整 ELF，解析
dynsym/本地符号/`.gnu_debugdata`，兼容 `std::__ndk1` 与 `std::__1` 两种 ABI，安装
inline hook，并额外挂接 passthrough PLT。它证明私有实现可被工程化追踪，但也直接证明
维护面是 ROM/Mainline 私有 ABI，不是 PathGuard 要求的稳定接入点。

MaterialCleaner 使用 Xposed Hook `FuseDaemon`/`MediaProvider` 私有 Java 方法，适用于它
自身的 Provider 兼容目标；原始 syscall、目录 lookup 与 cache 完整性仍不构成 exact
hide 保证，不能替代 direct-VFS backend。
